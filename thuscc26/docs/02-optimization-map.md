# HPL 优化：先弄清对象，再动一个因素

## 目标和约束

目标是在比赛允许的资源内，**残差 PASSED，并提高 GFlop/s**。已有手动参考值：N=120000、NB=384、P×Q=8×14、112进程、每进程1线程，4072.2 GFlop/s。

HPL用标准工作量除以内部求解时间估计速率：

```text
GFlop/s = [(2/3)N³ + (3/2)N²] / 求解秒数 / 10⁹
```

实际读程序结果表；表中的时间和性能已经舍入，手算有小差异。固定 N 时，相同任务更快意味着速率更高；换 N 后任务量不同，不能直接按秒数比较加速比。队列等待不属于求解时间。

## 哪些文件控制哪些因素

| 可调因素 | 修改位置 | 为什么可能变快 | 要保持的一致性 |
|---|---|---|---|
| NB 分块大小 | 每次实验的 `HPL.dat` | 影响 BLAS 矩阵乘法效率、缓存利用、面板与通信开销 | 先保持N、P/Q、进程线程、二进制不变 |
| P×Q进程网格、映射 | `HPL.dat`，必要时配合绑定 | 改变数据分布和通信路径 | P×Q等于MPI进程数；总核数合规 |
| MPI进程数、每进程线程 | Slurm资源项、`mpirun`、环境变量、库链接 | 平衡跨进程通信与节点内共享内存计算 | 进程×线程不超实际申请核数；同步改P/Q |
| BLAS / MPI实现与版本 | 编译配置、`module`、运行环境 | 矩阵内核和通信实现影响大量时间 | 重新构建，核对实际链接，库与MPI启动器匹配 |
| 编译器与选项 | `Make.Linux_Intel.in`或新模板 | 影响向量化、指令集与优化 | 每种构建独立保存；不改源码和校验逻辑 |
| 进程绑定、NUMA放置 | 运行脚本的MPI选项/环境变量 | 减少进程迁移、跨插槽内存访问 | 先查实际CPU布局与MPI说明，不盲目照抄 |
| N规模 | `HPL.dat` | 较大计算可能摊薄通信开销 | 内存约8N²字节加额外开销；工作量约N³ |
| BCAST、DEPTH等算法参数 | `HPL.dat` | 改变通信拓扑及计算与通信重叠 | 少量有依据候选，记录与NB/网格的相互影响 |

节点通常是独立服务器。Slurm按照分区和空闲资源分配节点；同一分区也应核对配置是否一致。先记录节点与运行条件、用重复测量估计波动，再判断改动是否有效。指定节点须以实际可用资源与比赛规则为准；两次不同节点相差约0.64%不足以证明节点或参数造成变化。

## 第一轮该怎么思考

1. **提出假设：** “NB影响矩阵运算效率，调整NB可能改善当前基线。”
2. **固定条件：** N120000、112进程×1线程、P8Q14、同一二进制和软件环境。
3. **少量筛选：** 比较 NB336、384、448；384是参考，不预先认定另外两个更好。此处是待用户操作的计划，没有新实验结果。
4. **每次独立目录：** 准备副本、检查只改NB、手动提交一次、保存完整日志。
5. **先验正确再比性能：** PASSED才比较GFlops；记录节点、作业号、构建、参数和异常。
6. **确认收益：** 小幅变化先复测基线与候选；若运行条件可比，用多次结果的中位数比较，并报告波动。不要只挑偶然最快的一次来证明参数收益。
7. **再研究交互：** NB筛选后研究P/Q；网格变化可能改变最佳NB，必要时对少量组合再验证。

固定任务时可报告：`加速比 = 基线求解时间 / 新求解时间`。同 N、同标准工作量时近似等于 `新GFlops / 基线GFlops`。所有候选试完再据实选择，不把本地练习、旧作业和比赛集群结果混算。

## 遇到类似题目的通用流程

读规则和评分 → 固定可复现baseline → 了解硬件/软件和主要耗时 → 将假设映射到可调文件 → 控制变量做少量实验 → 检查正确性与波动 → 验证候选及交互 → 保存可复现材料与原始证据。

当前源码限制来自[比赛原题](https://lab.cs.tsinghua.edu.cn/scc/Benchmarks/HPL/)。参数原理可查发布包中的 `TUNING` 和 [Netlib调优说明](https://www.netlib.org/benchmark/hpl/tuning.html)。Intel MPI不要显式设 `I_MPI_OFI_PROVIDER=verbs`；保留默认选择。
